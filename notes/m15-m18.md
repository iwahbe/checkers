# Working plan: M15–M18

The plan for the milestones Ian set on 11/11/2026 (D114–D116), written so
the work can go on unattended and survive a summarized context. SPEC.md is
the source of truth; this file is only the order of work and the baselines.

## Rules for the whole run

- After each milestone: `checkers fmt --check`, `cargo clippy --all-targets`,
  the full test suite against the pip Z3 (dev build) and the vendored Z3,
  every changed `.out` read, SPEC's milestone row marked done with what was
  measured, a commit, a push, and a Memory note.
- A choice the spec doesn't settle is recorded in §0 as **(proposed)** and
  the most reasonable reading is taken; the work goes on. Stop only for
  something that can't be undone.
- If a milestone stalls (no progress after a serious attempt), commit what
  is sound, record the state in its SPEC row, and go on to the next one;
  M16, M17 and M18 depend only on M15.
- Never weaken a test or an expected output to make it pass.

## M15: streams and processes (D112)

1. The resource check: a value whose type depends on something not known
   where it is used (`sp~Spawned ss` for an unknown `ss`) counts as a
   resource. Golden test first (`tests/types/`), then the fix in
   `src/usage.rs`. Also E0401 shows the type normalized (`File`, not
   `pipe_end Pipe`).
2. `std.files`: `read_some n f`, `read_exactly n f`, `read_rest f`,
   `write_bytes b f`, each `(Result … IoError, File)`; `File` in the runtime
   becomes a handle on a file descriptor of any kind.
3. `std.terminal`: `stdin`, `stdout`, `stderr`, each a new `File` sharing the
   stream's runtime buffer with the other handles and with `print_line` etc.
4. `std.proc`: `Stream` (`Inherit`, `Pipe`, `Discard`), `Streams`,
   `pipe_end`, `Spawned ss`, `Child`, `Output`, `run`, `spawn`, `wait`;
   `exec` stays. `run` writes the input and reads both outputs at once.
5. Builtins in `rt/src/builtins/{files,terminal,proc}.rs`; §16.3 rows
   updated (`tests/std.rs` checks the table).
6. Switch over: every example, tool and test that reads or writes a stream
   uses the new operations where they fit (e.g. `tools/fmt.ck`'s standard
   input, `examples/wc.ck`, `examples/copy.ck`, `examples/json.ck`).
7. Tests: golden tests for each operation; `tests/run/` cases for `proc.run`
   and `proc.spawn` (the child can be `ckc` itself, or a small `.ck` program
   built by the test).

## M16: blocking operations free the thread (D113, §13.8; Linux x86-64, D116)

1. Audit the runtime for what can't follow a behaviour to another thread:
   `TRAP` (thread-local, `rt/src/prog.rs`), the `Mutex` inside each cown's
   `Cell` (`rt/src/obj.rs`), any other thread-locals.
2. Stacks: a pool of reserved (not committed) 256 MiB stacks with a guard
   page; a context switch in `asm!` for x86-64 (callee-saved registers,
   stack pointer). Each behaviour runs on a pool stack.
3. The poller: one thread on `epoll`; non-blocking pipes and terminals;
   reads and writes that would block register and park.
4. A thread pool for regular-file I/O and `waitpid`.
5. `clock.sleep` only if `Clock` has it by then (it doesn't today: skip).
6. Done when (§13.8): with `--threads 2`, a program whose behaviours wait on
   more pipes than it has threads finishes (`tests/stress/` or `tests/run/`
   case); the stress tests pass; `bench/behaviours.ck` within 10% of the
   baseline below.

## M17: sound reflected definitions (§7.3, D116 b)

1. Look for a program that today's encoding lets Z3 prove something false
   about: a reflected function with `decreasing` recursion whose equation,
   taken for all solver values (including ones the recursion never reaches,
   or that violate its precondition), is inconsistent or implies a false
   fact. Look at `src/verify/smt.rs` for how definitions are emitted.
2. If none can be found after a serious search: record in §7.3 what was
   tried and why it is safe, mark M17 done that way.
3. If one is found: golden test first (`tests/types/`, expected: the
   obligation unproven), then guard definitions as Dafny and F\* do (typing
   predicates and fuel), fix the proofs that relied on the old encoding,
   record the encoding as a proposed decision, compare proving time with the
   baseline below.

## M18: no admits in std, `--release` (§7.4, D116 c)

1. Prove `string_render` and `members_render` in `stdlib/json.ck`. Any new
   axiom about a builtin is proposed in §0, not added silently.
2. `ckc build --release` and `checkers build --release`: refuse a program
   whose transitive ledger (dependencies and std included) has an `admit`,
   naming each with its location. Golden test (a `tests/tool/` command or a
   `tests/run/`-style case).
3. Every example builds with `--release`; `ckc trust examples/json.ck` lists
   no `admit`.
